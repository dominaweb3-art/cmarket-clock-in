# M4: durable state foundation and Symmetry review

Date: 2026-09-22 (America/Bogota). Classification: SHARED. Mainnet execution remains disabled.

## Track A — scope and limits

`services/c3-mainnet` now has a NodeNext TypeScript build, a clean ignored `dist/`, and a single package export: a read-only service-status facade. The PostgreSQL forward migration `0001_c3_state.sql` defines intents, immutable authorizations, idempotency, evidence, RPC observations, snapshots, manifest events, recovery attempts, transactional outbox and append-only audit records. It uses PostgreSQL `numeric` for raw monetary units and `timestamptz` for time. The internal server-only repository uses serializable transactions, revision-guarded compare-and-swap, database-time recovery limits, and a bounded outbox delivery lease. The generic state transition cannot mark an intent settled; only independently verified evidence can do that.

At the M4 checkpoint, this was **not production-validated durable persistence**: no disposable PostgreSQL instance was available. M4.1 results appear below. The existing builder authorization context, vault snapshot registry, manifest lifecycle and reconciliation pipeline are still in-memory. The repository is not yet wired into them, so a service restart cannot restore the entire C3 execution pipeline. The migration includes snapshot, RPC-observation and manifest tables, but reviewed write/read paths and integration tests for those aggregates remain to be implemented. `DURABLE_PERSISTENCE_READY = false`.

The outbox only delivers safe metadata; webhook delivery must be idempotent by event ID. It does **not** retry deposits, swaps, signatures or settlement. The audit log is append-only at the database trigger level, not independently tamper-proof against a privileged database operator.

The only environment variable this foundation reads is server-side `DATABASE_URL`. It must never be prefixed `EXPO_PUBLIC_`, committed, logged, or placed in an APK. No production database was contacted. The compiled package is private and must not be published. Internal compiled modules still exist for a future server process, but only `dist/public.js` is package-exported.

Before a production-readiness claim: provision a disposable PostgreSQL instance; apply migrations from an empty database; test restart/reload, immutable authorization verification, two-writer CAS, concurrent conflicts, key duplication, recovery attempts 1–4 and 24-hour expiry, signature preservation, rollback, outbox delivery and leases, snapshot/manifest provenance, corrupt rows, monetary boundaries and audit append behavior. Then wire the repository through builder, keeper and reconciliation without weakening sealed evidence, independently review the change, and repeat the tests. Do not connect to production merely to satisfy this checklist.

## M4.1 local PostgreSQL evidence and remaining gate

On 2026-09-22, a disposable PostgreSQL 16 cluster bound to localhost was started from an isolated temporary directory. The versioned migration created exactly ten `c3` tables; the runner recognized a second application without duplicating objects. A separate temporary database user/database was created, and the test cluster was stopped and its own temporary files removed after each run. No existing or production PostgreSQL cluster was contacted.

Nineteen real-PostgreSQL test cases passed: migration/schema check; independent-connection CAS race; concurrent idempotency conflict; authorization storage/reload and immutable-update/delete rejection; submitted-signature reload; single-writer outbox lease; append-only audit rejection; exact u64 and u128 round-trips with overflow rejection; bounded recovery attempts 1–3 and manual review on the fourth; 24-hour recovery cutoff with signature preservation; corrupt authorization fail-closed; SQL injection treated as data; rollback of intent/idempotency when outbox insertion fails; failed-transition outbox isolation; expired lease reclamation; bounded dead-letter behavior; migration-checksum rejection; timestamp/index inspection; and manifest append-only/duplicate-revision rejection. M4.1B added a **real process boundary**: one Node process writes a synthetic, sanitized authorization and signature, exits, and a second Node process reconnects to the same temporary database and verifies both. This does **not** prove builder/policy recovery after restart. These tests prove selected repository guarantees, **not** all 30 requested cases. Snapshot provenance, manifest transition ordering and evidence binding, webhook idempotency, interrupted connections and full lifecycle restart still require real integration tests.

The migration now creates a dedicated `c3` schema, schema-qualified immutable trigger functions and selected foreign-key/work indexes. The server repository bootstrap validates migration checksum and refuses an absent/mismatched schema; local tests use isolated credentials. Nevertheless, compiled internal service modules still contain builder authorization maps, keeper evidence maps, snapshot maps and the in-memory manifest repository. The package export boundary exposes only the read-only facade, but that does **not** constitute full lifecycle durability. No production bootstrap binds these modules to the PostgreSQL repository. `POSTGRES_SCHEMA_READY` and `DURABLE_PERSISTENCE_READY` remain **unapproved** pending comprehensive tests and review; `FULL_LIFECYCLE_DURABILITY_READY = false`.

This M4.1 foundation is a local checkpoint, not an approved deployment. The 19 real PostgreSQL cases validate the schema and selected repository guarantees; they do not satisfy the 30-case matrix or production builder/submission durability. Do not enable Mainnet or advertise vault redemption from it. Next: complete the 30-case matrix, then connect builder and submission to durable state without weakening sealed evidence. Keeper, reconciliation, manifest lifecycle and Symmetry remain separate later gates.

### M4.1B production-wiring blocker

The current builder's registered policy intentionally uses a synthetic instruction payload, a placeholder share mint and a process-local authorization context. It is suitable only for disabled validation tests, **not** a real Symmetry deposit or a production policy. Replacing the process-local state with a database row would persist these placeholders, not make them safe or functional. The current manifest SQL stores immutable events but has no stable manifest lineage key or trigger that enforces legal transition order; the repository's in-memory validator is the only transition gate. The snapshot table stores hashes and amounts, not a complete canonical snapshot for independently verifiable restart recovery. Without an official reviewed Symmetry source/IDL/instruction contract and an approved production policy, no truthful builder→keeper→reconciliation→share settlement pipeline can pass the required lifecycle test. The correct gate is to keep the production facade read-only, Mainnet disabled, and `FULL_LIFECYCLE_DURABILITY_READY = false`; do not fabricate an adapter or report the synthetic test as blockchain evidence.
