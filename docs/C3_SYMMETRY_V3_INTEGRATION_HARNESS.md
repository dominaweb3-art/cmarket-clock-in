Este expediente no autoriza fondos ni es una prueba de compra/venta C3. Los valores observados pueden variar con slot, vault y versión. Fuente primaria: tarball oficial [`@symmetry-hq/sdk@1.0.22`](https://registry.npmjs.org/@symmetry-hq/sdk/1.0.22), `sha512-yopoVu6VnFiktGsjgeJ2dbFX8pdciePK7BUFNbUYb5wAto6DQqVq6a51qE33dRT6BRkL/ANBpKZEJgqpJX+KMA==`; `gitHead=7f83eed9866c1833149fbfdcaa93bd5ba9eed0da` **no vinculado a fuente pública reproducible ni binario on-chain**. ## Inventario API pública relevante

Fuente: `dist/index.d.ts` y JS compilado del tarball. `TxPayloadBatchSequence` contiene transacciones _sin firma_ codificadas, instrucciones, blockhash y ALT; **ningún método listado firma o envía por sí mismo**, pero cada builder consulta RPC y genera instrucciones con requisitos de firmante. El hecho de que el SDK documente un método no certifica la semántica del programa.

## Máquina de estados objetivo, no implementación operativa

Cada transición debe tener fila PostgreSQL durable con `intent_id`, wallet, vault, importes `bigint`, estado previo/nuevo, versión CAS, clave idempotente única, autorización (hash de mensaje), bloque/slot/firma, evidencia reconciliada y timestamp. Outbox y audit log conservan intentos y resultados inciertos. Los siguientes requisitos son **especificación**; el helper `assessResearchTransition` solo prueba invariantes, no toca DB ni red.

| Cambio                                                                          | Actor, aprobación                | Evidencia, plazo y recuperación                                                                                                |
| ------------------------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| draft → awaiting_wallet                                                         | usuario; sin firma aún           | quote/config fresca, intent y llave única; vence según quote                                                                   |
| awaiting_wallet → intent_submitted                                              | wallet/MWA, aprobación explícita | hash exacto firmado y firma persistida **antes** de transmitir; si interrupción, consultar cadena, no reenviar automáticamente |
| intent_submitted → vault_processing                                             | reconciler                       | finalización de cada depósito/lock y efecto USDC; ausencia/discrepancia → manual_review                                        |
| vault_processing → shares_issued                                                | keeper y reconciler              | share mint y owner del ATA, supply/intent verificables; expiración → manual_review o failed_recoverable sin retry              |
| shares_issued → active                                                          | reconciler                       | balance de shares y vault/intent finalizados; ninguna posición se infiere solo de DB                                           |
| active → redemption_requested                                                   | usuario                          | quote/USDC min-out verificables, llave nueva; aún no se permite por política                                                   |
| redemption_requested → shares_locked_or_burned                                  | wallet/MWA                       | firma aprobada, share debit exacto, intent finalizado; outcome incierto → manual_review                                        |
| shares_locked_or_burned → rebalance_pending                                     | keeper/reconciler                | subastas/swaps, activos, cuentas y rutas auditadas; parcial → partially_completed                                              |
| rebalance_pending → usdc_claimable                                              | keeper/reconciler                | balance USDC del vault reservado por intent, min-out; si no verificable → manual_review                                        |
| usdc_claimable → usdc_received                                                  | reconciler                       | `transferChecked` USDC finalizado al ATA del mismo usuario y sin debitos extra                                                 |
| awaiting_wallet/redemption_requested → cancelled/expired                        | usuario o reconciler             | solo con prueba de no submission y vencimiento; nunca cancelar efecto ya finalizado                                            |
| cualquier etapa incierta → failed_recoverable/manual_review/partially_completed | reconciler                       | firmas y evidencia retenidas; reanudación exige aprobación explícita y verificación on-chain; sin retry/reverse automático     |

Por transición: idempotency key `vault:wallet:intent:stage:version`, timeout inicialmente **no aprobado** (no se inventa cifra), firmas/rutas/ALT y programa Symmetry/Token/ATA/Compute solo según manifiesto independiente futuro; si no se conocen cuentas/programas exactos, `manual_review`. Una secuencia de varios mensajes **no es atómica**; se muestran etapas completadas y pendientes. Los plazos exactos y política de cancelación deben salir del programa/IDL y del producto.

## Política candidata y contrato

`research/symmetry-v3/integration-policy.ts` compara, para **el ejemplo público**, secuencia exterior, programas, discriminadores, payer, único signer, USDC source/destination/mint/amount, longitud, v0 y ausencia de ALT; rechaza mutaciones probadas. Siempre devuelve `BLOCKED`. **No** verifica todos los metas writable/signers por instrucción, data completa, ALT no vacía, inner CPI, SOL/WSOL, share destination, min-output, fee/bounty o efectos finalizados; estos son bloqueadores, no falsos positivos de seguridad. Reglas de producción estrictas deberán validar instrucción semántica byte por byte y efectos con dos proveedores independientes antes de habilitar nada. `integration-contract.ts` define nueve operaciones futuras, pero todas rechazan `C3_SYMMETRY_PRODUCTION_POLICY_NOT_APPROVED`. No se importa desde `src/public.ts` ni se añade al registry de producción. La capability Mainnet permanece `false` inmutable.

Las pruebas adversariales mutan **resúmenes sintéticos de campos seleccionados**, no una respuesta completa de SDK ni un mensaje v0 serializado; no certifican que la política cubra cuentas omitidas o instrucciones desconocidas. El probe real se inspeccionó por separado y no se guardó ningún payload. La aprobación de producción requiere fixtures realistas de SDK y transacciones finalizadas C3, con metas/data completas y casos hostiles.

`npm run c3:symmetry:integration-readiness` en `services/c3-mainnet` emite cada puerta y **siempre `OVERALL: NO_GO`** en esta fase. Ni el probe ni el test invocan MWA o wallets.

## Dependencia Pyth y salida

El HTTP 403 de Hermes autenticado impide una evidencia de precio actual, **no** el avance de un arnés de integración Symmetry. Estado operativo de participaciones e intents debe provenir de cuentas/finalidad Symmetry; NAV del vault únicamente cuando su layout/fórmula y activos reales estén verificados. Pyth Push leída en cuentas Solana podría ser monitor independiente en una fase futura, sin sustituir contabilidad Symmetry. No se calculó NAV vivo ni se contactó Pyth/Symmetry en M4.5.

Para pasar a producción: respuesta técnica oficial que identifique parámetro/ruta USDC y min-out, IDL y programa desplegado, auditoría y upgrade authority, layout completo de intents/acciones, C3 vault/activos/oráculos/liquidez/fees a **1 USDC**, buy→mint y burn→USDC finalizados en vault multi-activo, política independiente Security y gobernanza Squads. Hasta entonces: **C3 no desplegado ni ejecutable; Mainnet apagado; no promesa de cesta funcional**.
